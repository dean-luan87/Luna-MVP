# A 方案问题总结：从 pyttsx3 到 macOS say 的迁移

## 🔍 问题根本原因

### 核心问题：pyttsx3 在 macOS 上的兼容性缺陷

经过详细诊断，发现问题的根本原因是：

#### 1. **pyttsx3 在 macOS 上的结构性缺陷**
- **平台兼容性**：pyttsx3 的 `nsss` 驱动在 macOS（特别是 Sonoma、Sequoia）上存在已知问题
- **多进程不稳定**：官方已确认 `nsss` 驱动在多进程模式下无法稳定运行
- **播放中断**：`runAndWait()` 在 macOS 上可能被系统音频服务中断，导致播放到一半就停止

#### 2. **具体表现**
- ✅ 子进程能正常启动
- ✅ 语音引擎能正常初始化
- ✅ 能说出前半句
- ❌ 但 `runAndWait()` 在 macOS 环境下出错 → 播放中断
- ❌ 后续队列消息被阻塞，不再继续播放

#### 3. **诊断证据**
- **诊断脚本测试**：即使完全绕过项目逻辑，pyttsx3 仍然无法完整播放
- **日志显示**：技术层面 `runAndWait()` 返回成功，但实际音频输出被截断
- **用户反馈**：只能听到"测试一号 Luna 语——（被截断）"，后面完全没有声音

## ✅ 解决方案：A 方案（macOS say 命令）

### 为什么 A 方案能解决问题？

#### 1. **系统级工具，稳定可靠**
- `say` 是 macOS 系统自带的命令行工具
- 不依赖第三方 Python 库
- 直接调用系统音频服务，避免兼容性问题

#### 2. **设计优势**
- **非阻塞**：使用 `subprocess.Popen`，不阻塞主线程
- **可中断**：通过 `killall say` 可以随时停止
- **不叠音**：新播报会自动停止上一条（通过 `_stop_locked()`）
- **简单可靠**：代码量少，逻辑清晰，易于维护

#### 3. **实现细节**
```python
# 核心实现
cmd = ["say", "-v", "Ting-Ting", "-r", "180", text]
subprocess.Popen(cmd, stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
```
