## §1. 文档目标与适用范围

### 1.1 解决的问题

- 决策运行主链、白盒、日志与数据源调度层在工程上已**基本成形**，但复杂场景越来越多表现为 **主任务 / 子任务 / 插入 / 恢复 / 切换** 的长链协同问题。  
- 若任务链与主链**接口不清**，任务信息要么漂浮为「第二系统」，要么被误塞进主链拍板逻辑，导致越权与误判。  
- 需要**正式定义**：任务链如何进入主链、主链如何影响任务链、任务链关键状态如何进入白盒与日志。  
- 需要让 **任务链成为主链可依赖的状态来源之一**，与调度层、白盒、日志 **同链**，而非旁路叙事。

### 1.2 本文档的定位

| 是 | 不是 |
|----|------|
| `LUNA_MAINLINE_ENGINEERING_MAPPING.md` 后续工程补齐方向中的 **关键专题工程设计** | 完整任务系统或任务中心的 **实现说明书** |
| 回答「任务链如何进入主链 / 主链如何影响任务链 / 白盒与日志如何承载任务链状态」 | 任务图生成器、DAG 引擎、调度算法的 **实现文档** |
| 后续任务链与主链的 **工程接入约束** | 数据源调度 **算法** 或 **评分公式** 文档 |

### 1.3 约束效力

后续凡涉及任务链与主链的模块划分、字段归属、日志与白盒义务，**以本文件与上位总纲为准**；与总纲冲突时以 **总纲** 为准。

## §2. 任务链与主链的正式关系

### 2.1 主链（决策运行主链）

- 负责 **当前** 决策与 **当前** 收口。  
- 负责 **当前** 可执行的下一步（在安全与策略约束下）。  
- 负责即时的 recheck / fallback / recovery（语义见 `DECISION_MAINLINE_ARCHITECTURE.md`）。

### 2.2 任务链（Task Chain）

- 负责 **长期** 任务结构：主任务、子任务、插入任务、恢复关系、切换关系。  
- 负责 **任务级连续性**（跨多步、多轮），而不是单步决策的「一句话状态」。  
- 提供 **当前在任务结构中的位置**（阶段、模式、恢复目标等），作为 **上下文输入**。

### 2.3 写死边界（硬句）

# 主链不替代任务链维护长期任务结构。

# 任务链不替代主链对当前动作的最终拍板。

# 二者强耦合于同一运行闭环，但不是同一概念层。

**关系表述**：主链回答「这一步怎么走」；任务链回答「这一步在长任务里处于什么位置、下一步任务语义上该往哪走」。主链必须能读任务链状态；任务链必须能接收主链结果回流并更新自身，但 **不得** 绕过主链直接下达执行动作。

## §3. 任务链状态作为数据源进入调度层

### 3.1 为什么任务链要进入数据源调度层

任务状态本身是 **主任务上下文、当前阶段、子任务关系、恢复上下文、成功标准** 的重要来源。数据源调度层的职责是对多源信息做 **分类、排序、主导源判断、冲突整理**（见 `INFORMATION_SOURCE_SCHEDULING_ARCHITECTURE.md`）。若任务链不进调度层，则「当前该听环境的还是听任务的」会在主链内隐式打架，白盒难以对齐。

### 3.2 任务链在调度层中的地位

任务链状态源属于：

# 数据源调度层中的正式源类型之一（与「任务状态源」语义对齐）。

在既有六类源框架中，任务链主要与 **任务状态源（task_state）** 重合；长链语义（插入/恢复/暂停）应能通过该源类型 **可观察地** 进入参与源集合与主导源判断，而不是仅存在于模块内部变量。

### 3.3 任务链至少应提供的最小状态（概念层）

下列字段为 **调度层与主链共享的最小概念集合**（实现可映射为不同载体，本文不规定 schema）：

| 概念 | 含义（工程语义） |
|------|------------------|
| `task_chain_id` | 当前任务链实例标识 |
| `task_chain_stage` | 当前阶段（粗粒度即可） |
| `primary_task_id` | 主任务标识 |
| `active_subtask_id` | 当前活跃子任务（若有） |
| `task_mode` | main / subtask / inserted / recovering / paused 等 |
| `task_resume_target` | 恢复时应对齐的目标（主任务/子任务/检查点） |
| `task_success_criteria_summary` | 当前收口是否在任务语义上算「推进成功」的判据摘要 |
| `task_chain_context_summary` | 供调度层与主链入口消费的一语句任务上下文 |

**写死**：

# 上述内容为调度层的输入事实，不是主链之外另起的控制链。

# 任务链通过调度层进入主链入口状态，而不是绕过调度层「直接改主链决策类型」。

## §4. 主链如何读取任务链状态

主链在 **全周期** 应把任务链位置当作 **一等输入**，至少在以下阶段 **读取并受影响**（与 `DECISION_MAINLINE_ARCHITECTURE.md` 阶段划分对齐，此处强调任务维）：

| 阶段 | 任务链的典型影响 |
|------|------------------|
| 当前场景整理 | 判定「当前首要矛盾」时合并任务阶段与场景（例：插入任务进行中则场景服从插入目标） |
| 候选路径形成 | 子任务/插入任务会收缩或偏移候选语义空间 |
| 主路径选择 | `task_mode`、阶段与主导源一致时优先选择与任务位置一致的路径 |
| 修正与再判断 | inserted/recovering 时 recheck 的「为何而证」不同；success criteria 影响是否需二次确认 |
| 收口 | 本次收口是否构成任务推进、子任务完成或仅局部合法 |
| 结果回流 | 收口结果映射为任务链状态迁移（见 §5） |

**典型影响（举例，非穷举）**：

- 当前任务阶段影响 **主导源判断**（任务紧迫阶段可能抬高 task_state 相对参考源）。  
- `inserted` / `recovering` 影响 **fallback / recovery** 的语义：是「任务内恢复」还是「环境侧保守」。  
- `task_success_criteria_summary` 影响 **本次收口是否算成功**（主链局部成功 vs 任务级未推进）。  
- `task_resume_target` 影响 **recovery 是否回到正确任务节点**（避免伪恢复）。

**硬句**：

# 主链不是只看「当前环境」，还要看「当前任务结构中的位置」。

## §5. 主链结果如何回流到任务链

### 5.1 主链输出可影响任务链的内容

主链每轮输出后，下列 **语义类别** 可能驱动任务链更新（概念层）：

- 当前任务是否 **推进**（相对上一任务链状态）。  
- 子任务 **完成 / 未完成 / 挂起**。  
- **插入任务** 是否结束、是否需回到主任务。  
- 是否进入 **pause / hold**（任务链级等待，与主链单步 hold 区分见 §6）。  
- 是否形成新的 **recovery 目标** 或 **恢复失败** 标记。  
- 是否暴露 **任务语义裂缝**、**目标漂移**、**假恢复** 等高阶信号（供白盒与总结消费）。

### 5.2 回流原则

**写死**：

# 回流不是直接写入长期记忆或图书馆。

# 回流首先改变任务链状态（或任务链可观察摘要）。

# 更新后的任务链再作为下一轮数据源经调度层进入主链。

闭环为：

# 任务链 → 数据源调度层 → 主链 → 任务链。

记忆、图书馆、后处理 **不得** 跳过「任务链状态更新」这一层去假装完成「任务级闭环」。

## §6. 任务链与主链的状态关系

两体系各有状态词汇，**禁止混用为同义词**。

### 6.1 主链状态（与架构文档对齐的粗分类）

- 候选态、执行态、恢复态、暂停态（语义以 `DECISION_MAINLINE_ARCHITECTURE.md` 为准）。

### 6.2 任务链状态（任务级）

- main、subtask、inserted、recovering、paused、completed、unresolved 等（可扩展，但须在文档层先定义语义）。

### 6.3 关键关系（硬句）

| 误区 | 正确定位 |
|------|----------|
| 主链 `recovery` = 任务链 `recovering` | **不等同**：主链 recovery 是一步内的再判断行为；任务链 recovering 是长任务结构上的恢复段。 |
| 主链 `pause` = 任务链 `paused` | **不等同**：主链 pause 多为采样/安全/确认上的暂停；任务链 paused 是任务生命周期上的挂起。 |
| 主链 `fallback` | 可能只是任务链某一节点上的 **保守收口**，不等于整任务失败。 |
| 主链一次 **success** | **不等于** 任务链整体成功；可能只是子任务局部成功。 |

# 禁止把「单步收口结果」与「任务级完成」混为一谈。

---

## §7. 任务链对白盒的进入方式

白盒必须把 **任务链位置** 纳入主链解释上下文，否则大量高阶问题会表现为「主链局部合理、任务级错误」。

### 7.1 白盒至少应能观察的任务链语义

- 当前 `task_chain_stage`。  
- 当前是 **主任务** 还是 **子任务** 主导。  
- 当前是否 **inserted / recovering / paused**（任务模式）。  
- 当前主链收口与任务链状态是否 **一致**（例如：收口宣称完成但任务链仍处于插入中）。  
- 是否出现：**task semantic crack**、**false recovery**、子任务完成但主任务丢失、**success criteria shifted** 等（与真实场景分类对齐，白盒以 **解释与标记** 为主，不替代主链）。

### 7.2 硬句

# 白盒解释主链时必须带任务链位置；否则易把局部正确误判为全局正确。

# 白盒只解释与关联，不反向修改任务链状态。

---

## §8. 任务链对日志与总结的进入方式

### 8.1 日志链（黑匣子 + 结构化事件）

至少应能承载：

- 当前任务链标识与阶段。  
- 当前任务模式（main / subtask / inserted / …）。  
- 任务恢复目标（resume target）摘要。  
- 主链对任务链的 **影响摘要**（推进/回退/插入结束/伪恢复标记等）。

**写死**：

# 任务链关键状态必须落在可追溯的运行记录中，不能只存在于白盒文案。

### 8.2 总结链（summary feed）

至少应能在总结入口中区分并摘要：

- 本次 **任务推进** 情况。  
- **子任务 / 插入任务** 处理结果。  
- 是否 **真正恢复主任务**。  
- 是否出现 **任务语义偏移**、**伪恢复**、**裂缝**。

**写死**：

# 任务链状态变化既要进黑匣子（可审计），也要能进入 summary feed（可浏览与对接后处理/图书馆读序）。

---

## §9. 任务链与白盒 / 日志 / 总结的一致性要求

### 9.1 对白盒

- 解释主链结论时必须能回答：**在任务结构的哪一步、何模式下** 得到该结论。  

### 9.2 对日志

- 任务链关键字段与主链影响摘要 **同帧、同 JSONL 可追溯**；禁止「白盒有、日志无」。  

### 9.3 对总结

- 总结必须能区分：**主任务是否推进**、子任务是否仅局部成功、是否伪恢复/裂缝。  

### 9.4 总硬句

# 主线—白盒—日志—任务链 必须同链。

---

## §10. 最小工程接入建议顺序

**建议顺序**（由浅入深，避免一上来任务引擎大重构）：

1. **定义最小 `task_chain_state_snapshot`（概念对象）**：承载 §3 最小字段子集，与现有 `task_chain_bridge` / 环境任务上下文等 **对齐命名语义**。  
2. **作为任务状态源进入 `scheduled_source_state`**：参与 `participating_sources` / 主导源 / 冲突摘要（与 M0 调度对象兼容）。  
3. **主链入口可读**：`mainline_integration` 或等价入口摘要中 **显式出现** 任务位置，而非仅散落在字段里。  
4. **白盒**：结构树 / 时间轴 / 第二层观察中 **带任务链位置** 的一句话或节点。  
5. **日志与 summary**：`run_summary_reference` 或并列字段中 **任务推进与模式** 可区分、可审计。  
6. **再考虑** 更深任务图、任务中心、跨轮持久化与治理联动。

**写死**：

# 不建议在未完成 1–3 前做完整任务引擎或任务中心。

# 先让「任务链是正式上下文」在调度层与主链入口成立。
