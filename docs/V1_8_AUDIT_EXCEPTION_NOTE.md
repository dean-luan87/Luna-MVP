# V1.8 冻结审计例外与解释说明

**版本**: V1.8  
**生效期**: V1.8 冻结窗口期  
**性质**: 工程治理文档

---

## 目的

本文档明确 V1.8 冻结审计中的例外情况，确保审计工具的输出能够被正确解释，避免因工具局限性导致的误判。

---

## 核心原则

### 冻结硬门禁条件

**唯一阻断条件**: `VIOLATION == 0`

- ✅ `VIOLATION = 0` → 冻结门禁通过
- ⚠️ `RISK > 0` → 需要人工审查，但不自动拒绝
- ⚠️ `WARNING > 0` → 需要人工审查，但不自动拒绝

### 审计工具职责边界

审计工具负责**检测**，不负责**解释架构职责边界**。

架构 owner 的声明优先于工具的自动判断。

---

## 已登记的审计例外（V1.8）

### 例外 1: `core/system_control.py` 缺失 RISK

**审计输出**:
```
[RISK] 核心接口文件缺失
- 缺失文件: core/system_control.py
```

**例外说明**:
1. `core/system_control.py` **不属于** V1.8 cognition kernel 的职责范围
2. V1.8 冻结范围聚焦于 `core/cognition/` 模块的判断逻辑
3. 系统控制层（system_control）属于基础设施层，不在本次冻结范围内
4. 此 RISK 为**信息性提示**，不构成冻结阻断条件

**治理决策**:
- 此 RISK 已被 V1.8 冻结规格明确接受
- 不影响 V1.8 冻结态的有效性
- 后续版本（V1.9+）可单独处理

## 审计结果解释流程

### 标准流程

1. **运行审计**: `python tools/v18_full_audit.py --ci`
2. **检查 VIOLATION**: 必须为 0
3. **审查 RISK/WARNING**: 对照本文档判断是否在例外范围内
4. **人工决策**: 架构 owner 确认是否接受例外

### 决策矩阵

| 审计结果 | 处理方式 | 冻结状态 |
|---------|---------|---------|
| VIOLATION > 0 | ❌ 必须修复 | 阻断 |
| VIOLATION = 0, RISK 在例外列表 | ✅ 接受例外 | 通过 |
| VIOLATION = 0, RISK 不在例外列表 | ⚠️ 人工审查 | 待定 |
| VIOLATION = 0, 仅 WARNING | ✅ 可接受 | 通过 |

## 例外登记原则

### 何时登记例外

1. **架构职责边界明确**: 文件/模块不在冻结范围内
2. **工具局限性**: 审计工具无法理解架构上下文
3. **已知技术债**: 已计划在后续版本处理

### 例外登记要求

1. **明确说明**: 为什么该 RISK/WARNING 可以接受
2. **职责归属**: 明确该问题属于哪个模块/版本的职责
3. **后续计划**: 如果适用，说明何时处理
