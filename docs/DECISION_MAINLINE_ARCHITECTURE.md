## §1. 文档目标与适用范围

### 1.1 解决的问题

- 决策运行主链如何从 **整理后的数据源状态** 开始运行，形成**当前判断、当前路径与当前收口**。  
- 如何保证主链**只负责当前决策与当前收口**，不侵占历史加工、图书馆、记忆与高层治理职责。  
- 如何作为后续 **白盒、日志、任务链接口、运行总结与后处理** 的**运行语义基础**（非实现绑定）。

## §2. 决策运行主链的正式定义

**决策运行链**是 Luna 的**核心执行主链**：在单一决策周期（或约定的节拍）内，完成从「已调度输入」到「可执行下一步或等价收口」的闭环。

**目标不是追求单次绝对正确**，而是：

- **持续可修正** — 允许沿同一条主链做有方向的校正；  
- **持续可收口** — 每周期尽量产出明确下一步或明确等待条件；  
- **持续可执行** — 避免长期停在不可行动的抽象卡死语义上。

**只负责**：

- **当前**输入面下的判断与路径选择；  
- **当前**收口（含澄清、保守落地、恢复尝试）；  
- **当前**结果回流（对当前闭环与下游入口负责）。

**不负责**：

- 历史经验的全量加工与长期策略沉淀；  
- 图书馆写入与检索执行；  
- 记忆筛选与写库；  
- 高层治理分析结论的替代主链拍板。

## §3. 数据源调度层与主链的关系

### 3.1 调度层的输入来源（概念分类）

至少包括：**用户输入源**；**环境观察源**；**任务状态源**；**记忆调用源**；**新信息 / 新观察源**；**外部策略 / 系统源**（含安全与策略类信号）。具体通道属实现层；本架构只要求**可被调度层识别与标注**。

### 3.2 调度层的职责

至少包括：**数据源分类**；**当前参与源识别**；**主导源判断**；**源冲突前置整理**；**优先级排序**；**时效性处理**；**主导源切换**（含动态相对静态、安全相对目标的优先级关系，见总纲）。

### 3.3 输出给主链的对象

主链**不直接消费**原始输入堆叠；调度层输出的是：

# 整理后的数据源状态

该状态须足以支撑主链做「当前场景整理」与「主路径选择」，**不**等价于「已决策」或「已下达 Action」。

### 3.4 写死边界

- **调度层不产生命令**（不对业务执行体下达最终动作指令）。  
- **调度层不直接输出 Action**（动作取舍属于决策运行链）。  
- **调度层只做前置整理与主导源调度**（含冲突与切换的可审计状态）。

## §4. 决策运行主链的阶段划分

主链按**概念顺序**分为六段；实现可映射为不同模块，但**语义不得打乱**。

### Phase 1：当前场景整理

回答：当前处于什么**场景**；当前**任务/子任务**语义；当前**阶段**；稳定性与风险粗判；是否存在**中断、冲突、漂移**等需进入修正段的信号。  
**本段不**做最终路径拍板。

### Phase 2：候选路径形成

形成 **hypothesis / candidate**、**fallback candidate**、**recovery candidate** 等**可能路径**；明确「当前可能怎么走」。  
候选**不等于**执行；候选可进入 watchlist / reserve（见状态模型）。

### Phase 3：主路径选择

确定 **当前主路径** 与**优先理由**；非主路径进入候选或观察，**不**并行当作已执行主链。

### Phase 4：修正与再判断

涵盖 **recheck**、**clarification**、**fallback**、**recovery**、**task stage shift** 等。

**硬规则**：

# 修正不是重新开始

# 修正是沿当前主链做有方向的校正

即：在已有主链语义上补证、澄清、保守落地或恢复，而非另起一条无关联决策链。

### Phase 5：收口为可执行下一步

产出须**尽量**明确为下列之一：**继续**；**澄清**（需用户/环境补信息）；**fallback**（保守可行动）；**恢复主任务**；**暂停/等待**（条件明确）。  

**硬规则**：

# 主链尽量输出「可执行下一步」

# 不长期停在 blocked_without_resolution 这类抽象卡死态

「卡死」若出现，应视为**工程异常信号**，须通过收口工具或澄清回落到可叙述、可执行的下一步或明确等待条件（实现层负责）。

### Phase 6：结果回流

判断：当前动作是否**有效**；用户是否**采纳**；环境是否**变化**；任务是否**推进/中断**；是否形成**后处理候选**（非写入记忆）。  
**主链在 Action 之后不结束**；必须完成**闭环回流**语义。

## §5. 主链状态模型

**工程显式化（M0.4）**：`mainline_state_snapshot` 将下文四态与 §4 六阶段映射为可观测字段，**只读对齐**本文语义，**不**改写拍板或收口逻辑；详见 `docs/MAINLINE_STATE_PHASE_EXPLICITNESS_M0_4.md`。

四态**不是**互斥标签的简单枚举，而是**层次化**运行语义；可与终端展示状态组合使用。

### 5.1 候选态（Candidate State）

- **只是可能路径**，尚未成为当前执行主路径。  
- **可被** watch / prune / defer（治理或内部策略语义，非本文件展开）。  
- **进入**：Phase 2 及主路径未锁定前。  
- **退出**：被主路径选择吸收或明确淘汰。

### 5.2 执行态（Execution State）

- **已形成当前主路径**，可指导当前行动或下一步。  
- **进入**：Phase 3 锁定主路径后。  
- **退出**：进入显式修正段、暂停态或完成本周期收口。

### 5.3 恢复态（Recovery State）

- **主链未整体重启**；在已有链路上做恢复、回正、补救。  
- **进入**：打断、偏移、插入任务、伪恢复等信号触发 recovery 语义。  
- **退出**：回到执行态或转入暂停/澄清。

### 5.4 暂停态（Pause / Hold State）

- **当前不宜继续推进**；等待 clarification、confirmation 或外部变化。  
- **必须有**可叙述的等待条件或退出条件（避免空转）。

### 5.5 切换与信号

| 切换类型 | 说明 |
|----------|------|
| 正常 | 候选→执行、执行→暂停（条件明确）、恢复→执行 |
| 异常信号 | 长期无出口、主路径反复漂移、澄清与 fallback 均不可用等（需工程与治理侧关注） |

## §6. recheck / clarification / fallback / recovery 的正式关系

四者均为 **主链收口工具族**，不是四条独立平行系统。

### 6.1 recheck

对**当前主路径**的再次确认或**局部补证**；**不是**重开决策。  
用于证据不足、环境变化、用户质疑等**沿主链**的补证。

### 6.2 clarification

在信息不足、目标不清、冲突较大时**主动澄清**；是**强收口手段**之一。  
产出须可导向**可执行下一步**或**明确等待条件**。

### 6.3 fallback

当前无法继续主路径时的**保守收口**；**必须尽量可行动**（最小风险、最小承诺、可验证）。  
**不是**放弃主链，而是**主链许可下的保守落地**。

### 6.4 recovery

在偏移、打断、插入任务、伪恢复等情况下，试图把主链**拉回有效路径**；**不**默认等价于全量重启。

### 6.5 关系总括

- **clarification / fallback / recovery** 均服务于**收口**；**不应**长期停留在「未动作 blocked」的抽象态。  
- **最终应尽量**将状态导向**可执行下一步**或**明确暂停条件**。

---

## §7. 结果回流与闭环

- **主链不以 Action 输出为终点**；必须有**结果回流**闭环。  
- **回流至少须覆盖概念维度**：用户反馈；环境变化；任务推进/中断；记忆片段调用**效果**（非写库）；是否形成**后处理候选**。

**硬规则**：

- **回流不等于直接写入记忆**。  
- **回流首先**影响**当前运行链**与**后续总结/后处理入口**；记忆写入由总纲与后置链约束。

---

## §8. 与任务链的边界与接口

- **决策运行链 ≠ 任务链**。  
- **主链**：当前决策与当前收口、当前回流。  
- **任务链**：长期任务结构、主/子任务、切换、插入、恢复关系（**不在本文展开**）。

**接口关系（概念层）**：

- **任务状态**作为**数据源**进入调度层，再进入主链；主链**不**直接实现任务引擎。  
- **主链输出**（推进、等待、恢复、中断处理）**再影响**任务推进/恢复语义。  
- 二者**强耦合、不同层**：主链负责「这一拍」，任务链负责「整条结构」。

## §9. 主线—白盒—日志一致性要求（主链视角）

### 9.1 对白盒

- 白盒解释的必须是**这条真实主链**上的事实与阶段。  
- **主链阶段、候选、收口、回流**必须**可被白盒观察**（具体层见 `WHITEBOX_OBSERVATION_ARCHITECTURE.md`）。

### 9.2 对日志

- **主链关键步骤**须能**原样**在落地链上可追溯。  
- **runtime_ctx / frame / JSONL** 等落地载体须能承载**主链真实状态**（字段级实现见日志专题）。  
- **benchmark / triage / rebaseline** 须读取**同一份**真实落地主链结果。

### 9.3 固定原则

# 主线真实运行

# 白盒真实解释

# 日志真实落地

主链侧义务：**运行真实发生**；**阶段与收口可对应**；**不制造旁路「假主线」**。

## §10. 主链质量判断原则（无公式）

- **不只看**最终是否 blocked；须看：
  - **上下文稳定度**；  
  - **主路径合理性**；  
  - **收口质量**（是否可执行或可澄清）；  
  - **恢复有效性**；  
  - **主导源切换合理性**（与调度层一致）。

- **高评分不等于逻辑正确**；须允许**表面健康但逻辑可疑**（伪稳定、伪恢复等）（与白盒与总纲一致）。
