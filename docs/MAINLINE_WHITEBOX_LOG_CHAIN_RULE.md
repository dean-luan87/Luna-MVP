# 主线—白盒—日志 固定执行规则（工程默认）

**完整形态上位总纲**：`docs/LUNA_MAINLINE_SHAPE_BLUEPRINT.md`（8 链、4 层、边界与数据流）。本文件定义**每轮交付的验证顺序**；总纲定义系统骨架，二者互补。

> 从文档此版本起，后续所有工程推进、修复、扩包、白盒接入、日志接入、benchmark/triage/rebaseline，**默认**按 **主线 → 白盒 → 日志** 顺序检查。这不是建议，是**固定执行规则**。

---

## 一、总原则

以后每做一轮工作，不管是：新功能接入、真实场景扩包、fix sprint、rebaseline、白盒增强、Console 调整、runtime_ctx / JSONL / logs 接入，都必须按以下顺序检查：

### 1. 主线是否通顺

先看真实运行链路是否跑通：

- 输入是否真的进入主链  
- 主决策路径是否清晰  
- recheck / fallback / recovery / task stage 是否合理  
- 主任务 / 子任务 / 切换 / 恢复是否真的发生在主链上  
- 是否存在「功能实现了，但主线实际没走到」的情况  

### 2. 白盒是否解释了同一条主线

再看白盒是否真的跟着主线走：

- 结构树是不是在解释当前真实运行链，而不是旁路摘要  
- 时间轴是不是当前真实事件链，而不是拼接描述  
- metrics / quality / optimization / feedback loop 是否围绕同一条链产生  
- 白盒字段是不是来自主链，而不是脱离主链单独生成  
- 是否存在「白盒看起来有内容，但不是在解释当前主链」的情况  

### 3. 日志是否完整落地

最后看日志是否把这条主线和白盒一起落下来：

- frame 是否写出  
- JSONL 是否写出  
- runtime_ctx 是否同步  
- case / benchmark / triage / rebaseline 读取的是不是同一份落地结果  
- 字段有没有丢失、错位、降级、写空  
- 是否存在「Console 看得到，但 logs 没有」「logs 有，但 benchmark 读不到」的情况  

---

## 二、固定输出要求（以后每轮都必须补）

后续每轮完成后，除修改文件清单、before/after、单测、smoke、文档等外，必须额外输出固定区块：

### 主线—白盒—日志 串联检查

格式固定如下：

#### A. 主线检查

至少说明：本轮主线入口是什么；主线是否真实跑通；主路径/收口路径/恢复路径是否符合预期；有没有主线未贯通的问题。

#### B. 白盒检查

至少说明：白盒是否解释的是同一条主线；结构树 / 时间轴 / quality / optimization 是否与主链一致；有没有白盒脱钩、旁路解释、伪解释的问题。

#### C. 日志检查

至少说明：frame 是否落地；JSONL / runtime_ctx / logs 是否同步；benchmark / triage / rebaseline 是否读取到本轮真实结果；有没有日志缺失、字段错位、未同步的问题。

#### D. 最终判断

只输出一个明确结论（四选一，不要模糊表述）：

- **主线通顺，白盒一致，日志已落地**  
- **主线有问题**  
- **白盒有脱钩**  
- **日志未完整落地**  

---

## 三、执行优先级规则

发生冲突时优先级如下：

1. **第一优先级：主线通顺** — 主线没跑通，不要急着优化白盒样式，也不要急着写漂亮日志。  
2. **第二优先级：白盒解释真实主线** — 主线跑通但白盒解释错链，优先修白盒对齐，不要继续扩功能。  
3. **第三优先级：日志完整落地** — 主线和白盒都对，但日志没写下来或 benchmark 读不到，优先修落地链。  
4. **第四优先级：再谈扩展与优化** — 只有主线、白盒、日志三者串起来后，才继续扩功能、扩场景、扩白盒层。  

---

## 四、禁止事项

- 只看 Console，不看 logs  
- 只看白盒摘要，不确认主线真的跑过  
- 只看 benchmark 结果，不确认它读的是本轮真实落地数据  
- 主线还没顺，就先补白盒样式/展示细节  
- 日志还没落地，就先做高层分析结论  

---

## 五、在文档中的落点

以后新增或更新交付文档时，若该轮涉及主链、白盒、日志任一项，文档中至少要加一小节：

### 主线—白盒—日志一致性检查

简单写清：主线是否通；白盒是否同链；日志是否落地。

## 六、适用范围

适用于后续所有：Real Scenario Pack 扩包、Targeted Fix Sprint、Post-Fix Rebaseline、Whitebox Reserve / Whitebox Plus 预留、Task Chain / Recovery / Recheck 相关功能、runtime_ctx / JSONL / Console / Benchmark / Triage 接入。

---

## 七、最终目标

后续工程不是只追求「功能做了 / 白盒有了 / 日志写了」，而是必须保证：

- **主线真实运行**  
- **白盒真实解释**  
- **日志真实落地**  

三者是同一条链，不允许各跑各的。
