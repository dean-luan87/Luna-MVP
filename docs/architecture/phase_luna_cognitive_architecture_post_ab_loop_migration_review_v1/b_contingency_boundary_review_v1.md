# B Contingency Reasoning Boundary Review

The new package uses B-CR terminology to avoid ambiguity with historical perception/dual-route Route B assets.

## Clean boundary

- B trigger and request are A-issued.
- B receives a bounded derived grant.
- B receives references, not authoritative state ownership.
- B result is non-binding and returns to A.
- A alone evaluates `USE`, `PARTIAL_USE`, `KEEP_AVAILABLE`, `SUPERSEDE`, `DISCARD`, or `REQUEST_UPDATED_B`.
- B cannot control Loop, create/split/merge Concern, recursively delegate B, declare World Truth, or own final Need/Sufficiency/Continuation.

## Historical conflict

`A Route` historical stage vocabulary contains `B Route` references in product/orchestration fixtures and older architecture. Those assets are orchestration/handoff chains or perception terminology and must not be treated as B-CR semantic ownership without an explicit adapter.

## Finding

B-CR boundary is contractually clean. The remaining risk is terminology and old route-chain interpretation, not a proven new B authority owner.
