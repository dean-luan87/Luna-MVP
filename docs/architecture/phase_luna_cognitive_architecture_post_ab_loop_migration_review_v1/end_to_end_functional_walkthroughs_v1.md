# End-to-End Functional Walkthroughs

These are static paper walkthroughs. No runtime is executed.

## Scenario 1 — short path: name on a sign

1. Brain owns the Concern and global governance.
2. A future Semantic Working Outline defines the bounded question.
3. Experience/Short-Path Filter compares prior information.
4. Existing Observation Gateway/Capability Governance could admit an OCR candidate, but the unified Semantic→Filter→short Capability contract is not implemented as one owner.
5. OCR evidence returns as a candidate; it is not World Truth.
6. If sufficient, Brain receives the result without A/B/Loop materialization; otherwise A receives the remaining gap.

Status: target contract is clear; current implementation gap is Semantic/Filter and short-path integration.

## Scenario 2 — A only: path blocked

1. Brain admits Concern and grants A.
2. A evaluates Current World/evidence and forms local Need.
3. A requests Observation/Capability through governed Requirement/Scope/Resolution/Admission paths.
4. Insufficient evidence produces A `REQUEST_MORE_EVIDENCE`, then A→Loop records only mechanical refs if persistence is needed.
5. New evidence creates a new state version; A judges relevance and sufficiency.
6. A emits `STOP_SUFFICIENT` or continuation; Loop mechanically closes/freezes if commanded.
7. Cognitive Outcome Candidate returns to Brain for assimilation.

Status: candidate seams support the control logic; unified real Observation request bridge remains missing.

## Scenario 3 — A + B-CR candidate coexistence

1. Brain grants A for one Concern.
2. A detects material uncertainty and issues a bounded B-CR request.
3. B receives derived authority and bounded refs.
4. A may remain ACTIVE while B is candidate-active, or A may be PAUSED/WAITING.
5. Environment/state changes; A compares current state with B source state.
6. A uses, partially uses, keeps, supersedes, discards, or requests updated B.
7. B never controls Loop or resumes A automatically.

Status: contract and candidate bridge are complete; no real concurrency/scheduler exists.

## Scenario 4 — Role/Field/Task/Emotion change

1. Role, Field, Context, Task or Emotion owner emits a new authoritative/candidate reference.
2. A/B receive the changed refs through a working envelope.
3. A judges whether the change affects meaning, relevance, Need, Hypothesis, sufficiency or continuation.
4. Brain/Grant governance decides whether old authority must be revoked or narrowed; no unified invalidation source currently exists.
5. Loop stores the new state/version and mechanically pauses/waits/replans only after an A/Brain command.
6. Old B results/Requirements become stale when source state, scope or relevance changes.

Status: ownership direction is clear; propagation and grant invalidation are a contract gap.

## Scenario 5 — Concern split

1. A detects that one local concern contains two independent concerns.
2. A produces `NewConcernCandidate` only.
3. Brain admits, rejects, defers or merges it.
4. If admitted, Brain governs separate A/Loop work contexts.
5. Existing Concern remains or becomes superseded only through Brain governance.

Task, B and Loop cannot split concerns. Current split/merge is reserved/candidate-only rather than runtime materialization.
