# LUNA：统一输出裁决口（V1）

## 1. 目标

当“视角链 × 语义链 × 任务链”打通后，系统会同时产生多路候选输出：

- 视角链想直接播报危险
- 语义链想补充解释
- 任务链正在执行当前任务
- 播报层不能同时说三句话

如果没有统一裁决口，必然出现：

- 重复播报 / 互相打断
- 低价值信息冲掉任务链
- 危险信息反而说慢了

本文件定义一个**逻辑上的统一输出裁决口**（不实现代码）：

> 最后到底是谁决定“现在说什么、先说什么、哪些不说”？

## 2. 原则（写死）

- **安全优先**：安全风险永远高于解释与丰富信息
- **单一出口**：对用户的“可听/可见输出”必须有唯一裁决口径
- **不越界**：裁决口不替代各链路推理，只做选择/排序/丢弃/降级/延后
- **宁可 unknown**：不确定时宁可不播报/请求澄清，也不要误导

## 3. 输入来源（候选输出池）

统一裁决口的输入至少包括：

### 3.1 视角链输出（Vision）

- `RiskEvent`：风险等级/原因/建议行为（可抢占）
- `EnvironmentState`：环境变量/限制变量（多为上下文更新）
- `DetailEvidence`：OCR/局部细节补证（默认不直接播报）
- `SummaryDecision.summary_packet`：视角汇总交付包

### 3.2 语义链输出（Semantic）

- 解释性提示（基于环境变量/补证的解释）
- 澄清问题（请求补拍/确认）
- 交互策略（如何说、什么时候说）

### 3.3 任务链输出（TaskChain）

- 当前任务关键提示（下一步动作、确认点、执行状态）
- 任务中断/挂起/恢复事件

### 3.4 风险/安全链输出（Safety）

> 若风险链与视角链合并，此处可视为同源；本节强调其优先级与抢占语义。

- 即时安全播报候选（必须抢占）
- 安全模式切换建议（例如“建议停下再拍”）

### 3.5 系统状态/运行态输出（Runtime）

- 当前是否正在播报（speaking / cooldown）
- 当前任务是否可被打断（task_interruptible）
- 用户状态（是否在驾驶/是否可交互，若存在）
- 速率限制与降噪（避免刷屏/刷语音）

## 4. 输出裁决口职责（写死）

裁决口负责：

- 决定是否播报
- 决定播报优先级与顺序
- 决定是否抢占/打断当前输出
- 决定哪些信息只入白盒、不外显
- 决定哪些信息留给用户追问时再答
- 决定输出的降级/合并策略（例如把多条合并为一句）

裁决口不负责：

- 不生成最终播报文案（文案由语义/播报层负责）
- 不替任务链做执行决策
- 不替视角链做感知推理

## 5. 最小优先级规则（V1）

### 5.1 输出优先级（从高到低）

1. **即时安全播报**
2. **当前任务关键提示**
3. **环境上下文更新**（默认不直接播报）
4. **低优先级丰富信息**（可延后/合并/丢弃）

### 5.2 可抢占 / 只能排队 / 必须丢弃

- **可直接抢占（preempt）**：
  - `risk_level=danger` 的安全播报候选
- **只能排队（enqueue）**：
  - 当前任务关键提示（若不冲突安全播报）
- **必须丢弃（drop）**：
  - 与当前任务无关、且不提升安全/执行质量的低价值信息（尤其在高负载/用户忙时）

## 6. 冲突处理规则（写死）

### 6.1 视角风险 vs 任务链

- 风险为 `danger`：风险优先，可打断任务链输出与执行提示
- 风险为 `caution`：允许任务链继续，但裁决口可插入“注意/减速”类短提示（不应刷屏）

### 6.2 语义解释 vs 即时安全播报

- 即时安全播报优先于解释
- 解释必须延后，并允许被合并为一句（“先安全，后解释”）

### 6.3 OCR/细节 vs 当前主任务无关

- 默认只入白盒或作为语义层上下文，不直接播报
- 仅当满足“任务强相关 + 置信度足够 + 不与安全/任务冲突”时，才进入任务链或可播报

### 6.4 多条信息同时到达（最小裁决顺序）

1. 安全播报候选（若有 danger 直接抢占）
2. 当前任务关键提示（必要时排队）
3. 语义解释/澄清（合并/延后）
4. 环境更新/低价值信息（白盒或延后）

## 7. 最小输出类别（V1）

- 即时安全播报
- 当前任务关键提示
- 背景上下文更新（不直接播报）
- 白盒留痕
- 用户追问时才回答的信息

## 8. 打断与恢复（V1）

### 8.1 哪些输出可以打断当前播报

- danger 级安全播报：必须可打断

### 8.2 被打断后是否恢复

- 被打断的“任务关键提示”：允许恢复，但可降级/合并
- 被打断的“解释性内容”：默认不恢复原样，改为合并摘要或留作追问

### 8.3 恢复时如何降级或合并

- 多条同类提示：合并为 1 条
- 过时提示：直接丢弃（尤其环境更新类）

## 9. 白盒观测（最小集合）

至少记录：

- 候选输出列表（来源：vision/semantic/task/safety/runtime）
- 最终选中输出（类别、优先级、是否抢占）
- 被丢弃/降级/延后的候选输出与原因
- 是否发生抢占/打断/恢复

## 10. 当前阶段不做项（写死）

- 不实现运行时仲裁器
- 不实现复杂排队系统
- 不设计具体文案
- 不引入新模型
- 不做完整多轮对话调度

## 一句话收束

先把三条链进入输出前的统一裁决规则写清楚，再进入后续真正的播报/反馈实现阶段。
