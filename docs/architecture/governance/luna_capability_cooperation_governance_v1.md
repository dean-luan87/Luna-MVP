# Luna Capability Cooperation Governance v1

## Cooperation Model

Capabilities cooperate by providing bounded, traceable candidate contributions under shared governance references. No Capability may directly grant another Capability permission, alter a peer's lifecycle, or upgrade a peer's output to Fact.

```text
Vision → Evidence Candidate
OCR → Text Evidence Candidate
        ↓
Translation Layer → Cognitive Primitive Candidate
        + Context reference
        ↓
future Cognitive Analysis candidate input
```

## Cooperation Rules

- Each contributor retains source, provider, Contract, uncertainty, and trace references.
- Combination requires Protocol compatibility, contextual suitability, and existing Permission/Admission review before a future execution context may exist.
- A combined result retains all contributing evidence; it cannot hide conflict or silently replace a source.
- Cooperation is not an authority merge: State mutation remains Reducer-only and Fact/Decision/Action require separate governance.

## Competition and Coexistence

Multiple Vision, OCR, Navigation, or other Capability variants may coexist as governed candidates. Fitness comparison may recommend a candidate selection or fallback set, but there is no automatic winner, provider replacement, deprecation, or retirement. Coexistence must preserve compatibility records and historical trace.

## Capability History Boundary

Capability history may retain performance, failure, adaptation, and usage-context evidence for governance assessment. This history is neither Luna Memory, Experience, Knowledge Base, nor Fact Store. A Capability may not write Luna Memory directly; any future learning handoff remains review-bound under existing Learning Candidate Governance.
