# Future Implementation Entry Rules

Freeze Status: `ARCHITECTURE_FREEZE_CANDIDATE`

These rules govern how a future module may enter Luna after the Dynamic Cognitive Architecture v2 freeze is approved. They are development admission rules, not permission to implement, activate, or migrate any module during M5.

## 1. Mandatory module declaration

Every new module must define all of the following before implementation:

1. **Owner** — the one governance authority responsible for the module's final state and contract.
2. **Input** — admitted data, evidence, references, candidates, policies, and provenance the module may consume.
3. **Output** — the exact Candidate, evidence, trace, or governed result the module may produce.
4. **Write Authority** — the one state or candidate scope the module may write.
5. **Forbidden Responsibility** — cognition, Reality, state, execution, ownership, persistence, or mutation powers the module must not acquire.
6. **Runtime Position** — `NO_RUNTIME_REQUIRED`, `FUTURE_RUNTIME_CANDIDATE`, `EXISTING_RUNTIME_CONSUMER`, or another separately governed status supported by evidence.

Missing or ambiguous declarations block implementation planning.

## 2. Architecture classification

A proposal must identify its position inside the frozen structure:

- Reality / Evidence;
- Field State System;
- Observation / Context;
- Personal Cognitive Network;
- Intent / Causal Reasoning;
- A/B Route;
- Decision Boundary;
- Task Lifecycle;
- Runtime Execution;
- Capability / Model;
- Outcome / Experience Compression / Memory;
- cross-cutting Constitution, Self, Social Self, Value, or governance boundary.

If a module cannot be classified without creating a parallel top-level cognitive path, it must stop and enter the freeze-exception process.

## 3. Contract and information-status entry

Before code work, the proposal must define:

- Candidate versus Fact semantics;
- provenance, trace, replay, revision, and revocation behavior;
- admission and failure behavior;
- source-owner precedence;
- compatibility aliases when an existing contract is involved;
- the condition under which an output may affect authoritative state.

Candidate schemas remain inactive until separately admitted. Model, Memory, Observation, PCN, simulation, and Runtime outputs cannot skip Reality Validation or their domain admission boundary.

## 4. Owner and Writer review

The proposal must prove that:

- no existing Owner is displaced by documentation wording;
- no second Writer is introduced;
- PCN does not absorb source-object ownership;
- Task Manager does not absorb Intent, Decision, Runtime dispatch, or Action;
- Model Manager does not absorb Reasoning or Decision;
- Runtime does not absorb Cognition;
- Memory does not absorb Reality or Decision.

Any conflict requires an explicit architecture-freeze exception and cannot be resolved inside an implementation phase.

## 5. Runtime necessity review

Runtime is not the default answer. A future module must first prove:

1. why architecture, contract, static capability, or existing Runtime integration is insufficient;
2. the exact admitted request and outcome-evidence envelopes;
3. the execution Owner and stop authority;
4. state, database, model, provider, network, device, and production-data permissions;
5. rollback, disablement, trace, replay, and recovery behavior;
6. why the implementation does not create a second Runtime mainline.

An adapter candidate is not an adapter implementation. A Runtime reference is not an active Runtime.

## 6. Engineering evidence and baseline discipline

Before implementation, reuse the relevant module baseline and existing asset inventory. A new full-repository scan is allowed only when the baseline is absent, an anomaly requires calibration, or a major version change invalidates it.

Architecture files may define future intent, but only code, active contracts, admitted registries, controlled validation, and explicit activation evidence can establish implementation status.

## 7. Required phase sequence

A future implementation normally requires:

```text
Architecture classification
        ↓
Owner and Writer review
        ↓
Schema / Contract candidate
        ↓
Compatibility and rollback review
        ↓
Runtime necessity and permission review
        ↓
Separately authorized implementation phase
        ↓
V0 / authorized V1
        ↓
User-terminal V2
        ↓
ChatGPT V3
        ↓
Separate activation or migration decision when required
```

Implementation, migration, and production activation are different authorities and must not be collapsed into one phase.

## 8. Freeze exception entry

If a proposal changes the frozen architecture, Owner boundary, Schema boundary, Contract boundary, Runtime boundary, dependency direction, or development governance, it must submit a future-only exception record containing:

- the requested exception;
- reason and affected scope;
- architecture and engineering impact;
- Owner and Writer effects;
- compatibility and rollback plan;
- risk and alternatives;
- separate approval, V2 verification, and V3 audit.

No implementation change can self-approve a freeze exception.

## 9. M5 non-activation boundary

M5 creates no implementation admission, Runtime, adapter, migration, provider integration, active contract, or active schema. These entry rules become a future development constraint only after the M5 candidate passes user-terminal V2 and ChatGPT V3 review.
