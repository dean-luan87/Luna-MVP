# M09 Role / Perspective — Module Review

## Identity and purpose

Canonical name: Role / Perspective inputs; no unified standalone canonical Role Governance module was found in the inspected repository. Related evidence is field-centric object-role planning and role-function lineage assets. If removed, the working envelope loses the actor/viewpoint constraints that qualify interpretation and relevance.

## Functions and authority

`CORE` intended function: provide governed role/perspective refs and structural interpretation constraints. `SUPPORTING`: role/perspective candidate inference in situation-understanding assets. Existing object-role planning is not evidence of global cognitive authority. Role/Perspective is `REFERENCE_ONLY` to A/B unless a source-owned role contract says otherwise; it may not decide Need, truth, sufficiency, action, or Loop state.

Responsibility is source integrity and versioning, but the owner is not consolidated: `OWNER_GAP`/`CONTRACT_GAP`. A owns semantic impact assessment; Brain owns global policy if role changes affect permission/safety/governance.

## Inputs, outputs, state, lifecycle

Inputs: role identity, perspective, field/context source refs, policy constraints. Outputs: versioned candidate/reference refs into Working Envelope and Current World formation. State is source/reference-only pending owner consolidation. Lifecycle: establish → update → invalidate dependent envelope/grants → A reassesses; actual propagation is not unified.

## Communication and negative boundaries

Allowed: Role/Perspective source→Working Envelope/A/State Formation; Brain may govern policy. Forbidden: Role→A semantic decision direct, Role→Loop, Role→Provider, Role→Concern mutation. B inherits bounded refs only.

## Walkthroughs

1. Normal: role/perspective ref enters envelope; A interprets local significance.
2. Invalid/stale role: version mismatch invalidates candidate/grant path; no automatic A decision.
3. Role change: source change→invalidation candidate→A impact assessment; Brain may regrant.

## Overlap, gaps, evolution, disposition

Overlap: `TERMINOLOGY_OVERLAP` role vs perspective vs field-centric object role; `STATE_DUPLICATION` risk in envelope/Current World. Gap: `OWNER_GAP`, `ADAPTER_GAP` for authoritative source/version propagation. It may evolve into a governed context provider, never a semantic reasoner. **Disposition: NARROW / REASSIGN (governance contract only, not new owner creation in this phase)**.

**Ledger summary:** authority = source integrity only, currently unclear; state = reference-only; receiver = envelope/A/State Formation; confidence = low-medium; status = unresolved owner.
